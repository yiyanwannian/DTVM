# DTVM内存桶大小说明

本文档详细说明DTVM项目中的内存桶大小设置、并发合约执行限制以及线性内存的概念。

## WebAssembly线性内存概念

WebAssembly的线性内存（Linear Memory）是WebAssembly模块的主要内存空间，它是一个连续的字节数组，可以被模块中的代码访问。

```
+------------------+
| 数据段          | ← 从模块的数据段初始化
+------------------+
| 全局变量        | ← 存储全局变量的值
+------------------+
| 堆区            | ← 动态分配的内存
+------------------+
| 栈区            | ← 函数调用栈和局部变量
+------------------+
```

线性内存的主要特点：

1. **分页管理**：WebAssembly线性内存按页管理，每页大小为64KB（65536字节）

2. **可增长**：可以通过`memory.grow`指令动态增长内存大小

3. **字节寻址**：使用字节级别的寻址，可以访问任意字节

4. **边界检查**：内存访问需要进行边界检查，确保不会越界

在DTVM中，每个WebAssembly合约实例都有自己的线性内存，这些内存通过内存桶模式进行管理。

## 内存桶大小设置

### 内存映射总大小

```cpp
// 当使用CPU陷阱检查内存溢出时，必须使用8GB的mmap大小，以避免访问其他已使用的地址
// 使用(size_t)8以避免表达式被解释为int32（4GB在int32中是零）
// 使用8GB而不是4GB的原因是i8.load base=INT32_MAX offset=UINT32_MAX会导致非常大的地址访问
constexpr size_t WasmMemoryAllocatorMmapSize = ((size_t)8) * 1024 * 1024 * 1024; // 8GB
```

DTVM使用`mmap`系统调用预分配一块8GB的虚拟内存空间。这个大小是为了确保即使在极端情况下（如访问接近32位地址空间边界的内存），也不会导致访问到其他已分配的内存区域。

### 桶项数量

```cpp
// 初始线性内存副本的数量，即内存桶文件包含的副本数
constexpr size_t WasmMemoryAllocatorBucketDuplicates = 10;
```

每个内存桶被划分为10个桶项，每个桶项用于一个WebAssembly实例的线性内存。

### 桶项大小

桶项的大小是动态计算的，但通常约为64MB（1000页）：

```cpp
// 在WasmMemoryAllocator构造函数中
size_t MmapMemoryBucketGrowMaxSize = 0;
// ...
// 计算单个初始文件大小
size_t SingleInitFileSize = InitMemorySize;
if (MaxMemorySize < SingleInitFileSize) {
  SingleInitFileSize = MaxMemorySize;
}
ZEN_ASSERT(SingleInitFileSize <= MmapMemoryBucketGrowMaxSize);

// 计算桶文件大小
size_t BucketFileSize = MmapMemoryBucketGrowMaxSize * WasmMemoryAllocatorBucketDuplicates;
```

桶项大小（`MmapMemoryBucketGrowMaxSize`）是根据WebAssembly模块的内存需求动态设置的，但不会超过内存映射总大小除以桶项数量：

```cpp
// 验证是否可以使用内存桶
if (WasmMemoryAllocatorMmapSize > 0 &&
    InitMemorySize > WasmMemoryAllocatorMmapSize / WasmMemoryAllocatorBucketDuplicates) {
  return false;
}
```

这意味着每个桶项的最大大小约为：8GB ÷ 10 = 800MB。但在实际使用中，通常限制为约64MB（1000页 × 64KB/页）。

### WebAssembly页面大小

```cpp
constexpr uint32_t DefaultBytesNumPerPage = 65536; // 64KB
```

WebAssembly规范定义每个内存页面为64KB（65536字节）。

### 内存增长限制

当WebAssembly代码执行`memory.grow`指令时，如果新大小仍在桶项的容量范围内，只需更新大小：

```cpp
bool InstanceUseMmap = OldUseMmap && (NewMemorySize <= MmapMemoryBucketGrowMaxSize);
if (OldUseMmap && InstanceUseMmap) {
  // 桶项有足够的空间增长
  const auto &NewMemoryData = WasmMemoryData{
    .Type = OldMemoryData.Type,
    .MemoryData = OldMemoryData.MemoryData,
    .MemorySize = NewMemorySize,
    .NeedMprotect = false,
  };
  return NewMemoryData;
}
```

如果新大小超过桶项的容量，则需要重新分配内存。

## 合约内存限制

DTVM对合约内存的限制有两个层面：标准WebAssembly限制和DTVM特定限制。

### WebAssembly标准限制

根据WebAssembly规范，内存页面数量的最大限制是65536页：

```cpp
constexpr size_t PresetMaxMemoryPages = 1u << 16;  // 65536 pages
```

这意味着理论上每个合约最多可以使用：

65536页 × 64KB/页 = 4GB 的内存

### DTVM特定限制

在DTVM中，对合约内存的限制取决于以下因素：

1. **内存桶模式限制**：当使用内存桶模式时，每个桶项的大小通常限制为约64MB（1000页），理论上最大可达800MB。

2. **DWASM模式限制**：在DWASM（可能是“硬件加速”或“区块链”模式）下，内存限制更严格：

   ```cpp
   #define DWASM_DEFAULT_MAX_VM_LINEAR_MEMORY_PAGES 256
   ```

   这意味着在DWASM模式下，每个合约最多只能使用256页，即：

   256页 × 64KB/页 = 16MB 的内存

3. **运行时配置限制**：可以通过运行时的`VMMaxMemPages`参数设置内存限制：

   ```cpp
   // 在Runtime类中
   uint32_t VMMaxMemPages = 0;  // 如果为0，表示无限制

   // 设置方法
   void setVmMaxMemoryPages(uint32_t Pages) { VMMaxMemPages = Pages; }
   ```

4. **内存映射文件限制**：当使用内存桶模式时，还有一个文件大小限制：

   ```cpp
   constexpr size_t MmapMemoryFileMaxSize = 32 * 1024 * 1024;  // 32MB
   ```

### 实际限制总结

综合以上因素，合约内存限制如下：

1. **标准模式**：
   - 使用内存桶模式时：最多64MB（1000页），理论上最大可达800MB
   - 使用单一映射或普通内存模式时：最多4GB（65536页）

2. **DWASM模式**：无论使用何种内存模式，最多16MB（256页）

在实际应用中，大多数合约的内存使用都远低于这些限制，通常只需要几个页面（几百千字节）就足够了。

## 并发合约执行限制

根据DTVM的内存桶设计，每个内存桶只能容纳10个桶项（`WasmMemoryAllocatorBucketDuplicates = 10`），这意味着在单个内存桶实例中，DTVM最多只能同时运行10个合约实例。

当所有桶项都被分配后，如果需要创建新的合约实例，有以下几种可能的处理方式：

1. **等待现有合约实例释放**：当现有合约实例结束执行并释放其桶项时，新的合约实例可以使用这些释放的桶项。

2. **创建新的内存桶**：理论上，DTVM可以创建多个内存桶实例，每个实例可以容纳10个合约。但这需要额外的内存开销，因为每个内存桶都需要预分配8GB的虚拟内存空间。

3. **使用非桶模式**：如果无法使用内存桶模式，DTVM会回退到单一映射模式（`WM_MEMORY_DATA_TYPE_SINGLE_MMAP`）或普通内存分配模式（`WM_MEMORY_DATA_TYPE_MALLOC`）。

在实际应用中，这个限制意味着如果需要同时运行大量合约，可能需要考虑以下策略：

1. **合约池管理**：实现一个合约池，限制同时执行的合约数量，并将其他合约请求排队。

2. **分片执行**：将合约执行分批进行，每批不超过10个合约。

3. **多实例部署**：部署多个DTVM实例，每个实例有自己的内存桶，可以处理更多并发合约。

## 高并发合约执行解决方案

DTVM项目采用了多种策略来解决合约高并发执行的问题，结合源码和文档，主要有以下几种方案：

### 1. 多线程并行编译

DTVM使用线程池来并行编译WebAssembly函数，显著提高编译性能：

```cpp
// 创建线程池，线程数量为配置的线程数和函数数量的较小值
common::ThreadPool<WasmFrontendContext> ThreadPool(
    std::min(Config.NumMultipassThreads, NumInternalFunctions));

// 按函数大小排序，优先编译大函数
std::sort(FuncIdxAndSizes.begin(), FuncIdxAndSizes.end(),
          [](const auto &LHS, const auto &RHS) {
            return LHS.second > RHS.second;
          });

// 提交编译任务
for (const auto &[FuncIdx, FuncSize] : FuncIdxAndSizes) {
  ThreadPool.pushTask([&, FuncIdx = FuncIdx](WasmFrontendContext *Ctx) {
    compileWasmToMC(*Ctx, Mod, FuncIdx, Config.DisableMultipassGreedyRA);
  });
}
```

这种方法可以显著减少合约的编译时间，使得在同样的时间内可以处理更多的合约。

### 2. 延迟编译模式

DTVM支持延迟编译模式（Lazy JIT），只在需要时才编译函数：

```cpp
// 启用延迟编译模式
CLIParser->add_flag("--enable-multipass-lazy", Config.EnableMultipassLazy,
                   "Enable lazy mode of multipass JIT");

// 延迟编译实现
void LazyJITCompiler::dispatchCompileTask(uint32_t FuncIdx) {
  if (CompileStatuses[FuncIdx] != CompileStatus::None) {
    return;
  }
  CompileStatuses[FuncIdx] = CompileStatus::Pending;
  ThreadPool->pushTask([&, FuncIdx](WasmFrontendContext *Ctx) {
    compileFunctionInBackgroud(*Ctx, FuncIdx);
  });
}
```

这种方式可以减少初始化时间，并将编译工作分散到合约执行的整个生命周期中，避免编译峰值。

### 3. 多种执行模式

DTVM支持多种执行模式，可以根据需要选择最适合的模式：

```cpp
// 运行时配置
struct RuntimeConfig {
  // 运行模式
  common::RunMode Mode = common::RunMode::SinglepassMode;
  // ...
};

// 根据模式选择执行方式
void Runtime::callWasmFunctionOnPhysStack(
    Instance &Inst, uint32_t FuncIdx, const std::vector<TypedValue> &Args,
    std::vector<common::TypedValue> &Results) noexcept {
  if (getConfig().Mode == RunMode::InterpMode) {
    callWasmFunctionInInterpMode(Inst, FuncIdx, Args, Results);
  } else {
#ifdef ZEN_ENABLE_JIT
    callWasmFunctionInJITMode(Inst, FuncIdx, Args, Results);
#else
    ZEN_UNREACHABLE();
#endif
  }
}
```

不同的执行模式有不同的性能特点：
- **解释器模式**：启动快速，适合短期运行的合约
- **单通道编译模式**：编译速度快，执行性能适中
- **多通道编译模式**：编译时间长，但执行性能最佳

可以根据合约的特点和运行环境选择最适合的模式，优化整体处理能力。

### 4. 内存模式选择

DTVM支持多种内存管理模式，可以根据需要选择：

```cpp
// 可以禁用内存映射
struct RuntimeConfig {
  // ...
  // 禁用mmap分配内存
  bool DisableWasmMemoryMap = false;
  // ...
};

// 内存分配模式
enum WasmMemoryDataType {
  WM_MEMORY_DATA_TYPE_NO_DATA = 0,    // 无数据
  WM_MEMORY_DATA_TYPE_MALLOC = 1,    // 普通内存分配
  WM_MEMORY_DATA_TYPE_SINGLE_MMAP = 2, // 单一映射
  WM_MEMORY_DATA_TYPE_BUCKET_MMAP = 3, // 内存桶模式
};
```

当内存桶模式不适用时，可以自动切换到其他模式，确保系统的灵活性。

### 5. 实现多实例部署

对于需要处理大量并发合约的场景，可以通过多线程启用多个DTVM实例，每个实例有自己的内存桶：

```cpp
// 创建多个运行时实例
std::vector<std::unique_ptr<Runtime>> runtimes;
for (int i = 0; i < numInstances; i++) {
  runtimes.push_back(Runtime::newRuntime(Config));
}

// 分发合约到不同的运行时实例
for (int i = 0; i < contracts.size(); i++) {
  int runtimeIdx = i % runtimes.size();
  auto& rt = runtimes[runtimeIdx];
  // 在选定的运行时实例上执行合约
  // ...
}
```

这种方式可以线性扩展并发处理能力，适用于高并发场景。

### 6. 虚拟栈与物理栈选择

DTVM支持虚拟栈和物理栈两种执行模式，可以根据需要选择：

```cpp
#ifdef ZEN_ENABLE_VIRTUAL_STACK
  VirtualStackInfo StackInfo(&Inst, FuncIdx, &Args, &Results);
  StackInfo.runInVirtualStack(&callWasmFuncFromVirtualStack);
#else
  callWasmFunctionOnPhysStack(Inst, FuncIdx, Args, Results);
#endif // !ZEN_ENABLE_VIRTUAL_STACK
```

虚拟栈模式可以提供更好的隔离性和安全性，而物理栈模式可能有更好的性能。

### 总结

DTVM的内存桶模式设计如下：

1. 使用`mmap`预分配一块8GB的虚拟内存空间
2. 将这块内存划分为10个桶项（`WasmMemoryAllocatorBucketDuplicates = 10`）
3. 每个桶项用于一个WebAssembly实例的线性内存
4. 每个桶项的大小通常限制为约64MB（1000页），但理论上最大可达800MB
5. 当WebAssembly内存需要增长时，如果新大小在桶项容量范围内，只需更新大小；否则需要重新分配内存

这种设计允许DTVM高效地管理多个WebAssembly实例的内存，同时提供内存保护和CPU异常检测功能。但这也意味着在单个内存桶实例中，最多只能同时运行10个合约实例，这可能成为高并发场景下的限制因素。

DTVM通过组合使用以上多种技术，实现了对高并发合约执行的支持：

1. **编译层面**：多线程并行编译、延迟编译和多种编译模式选择
2. **内存层面**：多种内存模式选择和内存桶机制
3. **部署层面**：多实例部署和负载均衡
4. **执行层面**：虚拟栈与物理栈选择

这些技术的组合使用使得DTVM能够高效地处理大量并发合约执行请求，同时保持良好的性能和资源利用率。
